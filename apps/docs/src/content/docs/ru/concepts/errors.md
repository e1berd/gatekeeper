Gatekeeper никогда не отправляет готовый к показу текст ошибки. Каждый сбой обозначается стабильным
`code`, а перевод — на стороне вызывающего.

## Контракт

Типизированная ошибка состоит из трёх частей:

- `code` — стабильный идентификатор вроде `INVALID_CREDENTIALS` или `STEP_UP_REQUIRED`. Это ключ
  локализации. Он часть контракта и меняется только со сменой версии.
- `message` — строка на английском для логов и трассировок. Запасной вариант для разработчика,
  никогда не показывается конечному пользователю и не переводится.
- `data` — необязательная структурная нагрузка для кодов, которым она нужна: `retryAfter` в
  секундах, `requiredAal`, метка времени `until` при блокировке. Форматируйте её в локали
  пользователя, не читайте как текст.

Клиент держит собственную таблицу текстов по `code` и процедуре, из которой он пришёл, и рисует их.
Набор `code` для каждой процедуры есть в контракте, поэтому таблицу можно сверить с ним.

## Как приходит код

| Поверхность    | Доставка                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------- |
| `/rpc`, `/api` | `{ code, message, data }`; в SDK `isDefinedError(err)` типизирует `err.code` и `err.data`    |
| `/form/*`      | `303` назад на исходную страницу с кодом в нижнем регистре в `?error=`; `data` отбрасывается |

Стандартные эндпоинты (`/.well-known/*`, колбэки OAuth и SAML) отвечают обычными HTTP-статусами,
потому что браузер обращается к ним напрямую.

## Перечисление аккаунтов

Поток входа схлопывает `USER_NOT_FOUND`, `INVALID_CREDENTIALS` и отсутствующую identity в один
`INVALID_CREDENTIALS`. «Нет такого аккаунта» и «неверный пароль» неразличимы по коду, по `data` и по
времени ответа. Нет эндпоинта, который сообщал бы, зарегистрированы ли email, телефон или логин;
проверка «занято ли?» в реальном времени на публичной поверхности — это перечисление, и она не
предоставляется.

## Валидация ввода

Сбои формата полей отделены от каталогов ошибок. Они приходят как issue валидации, обозначенные
`code` самого issue и `path` до поля — `invalid_format` в `["slug"]`, `too_small` в `["password"]`.
Контракт не задаёт своих сообщений в схемах, поэтому в поле формы нечему утечь на английском: клиент
сопоставляет код issue плюс path со своими текстами.

## Разрешение локали

Ответы API по замыслу не зависят от локали — они несут коды, а не предложения. Язык нужен только
поверхностям, которые Gatekeeper рендерит сам:

- транзакционные письма (верификация, сброс пароля, OTP, приглашение, оповещения об устройствах)
- страницы `/form/*` и их состояния ошибок

Они выбирают локаль из значения по умолчанию для realm, переопределяемого для каждого запроса
заголовком `Accept-Language`. Это работа M8, в текущем каркасе она не реализована; до тех пор
серверные строки только на английском.
